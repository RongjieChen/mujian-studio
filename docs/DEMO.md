# 参赛演示与下一轮验收

## 一句话定位

幕间帮助悬疑故事创作者，把故事变成可以修改、检查和交付的推理影游。Pi 执行案件设计与修复技能，固定游戏规则验证证据链，单台 DGX Spark 生成案件和镜头，玩家使用独立导出的作品。

## 五分钟演示

1. **0:00–0:40：让评委玩。** 打开已导出的短案件，先展示一位不肯透露关键信息的人物；拿到物证，再出示证据获得证词。清楚标注案件、图片、视频分别如何产生。
2. **0:40–1:30：让作品可改。** 展示人物、证据、场景与真相编辑器，给 Pi 一条明确修改要求；展示实际工具调用与保存版本。耗时较长的过程使用有时间标记的剪辑，不能伪装实时完成。
3. **1:30–2:45：证明 Agent 会解决问题。** 使用页面中的“注入证据死锁（演示）”，展示发布受阻；启动修复，展示最终只改变依赖、真相保持不变，以及修复后的通关路径。此处明确是故障注入演示，不冒充随机发现的真实用户错误。
4. **2:45–3:35：展示 Spark 实质工作。** 打开一次真实媒体作业的模型、种子、耗时和产物。展示第二次相同输入命中缓存，并说明缓存没有再次推理。
5. **3:35–4:30：交付作品。** 导出 HTML，在独立页面断开网络后试玩，证明作品不依赖创作端服务。展示另一份模型生成的案件，避免只有一个手写样例。
6. **4:30–5:00：说明边界与价值。** 已验证的是案件规则和制作流程；文学质量、跨镜头人物一致性、配音和长期稳定性尚需继续打磨。

提交前按组委会实际视频时长要求调整。B 站上传、公开仓库和报名材料由团队在正式提交时完成；当前按开发要求保留私有仓库。

## 评分如何落到可检查的成果

| 规则权重 | 展示的成果 | 还需补强 |
|---|---|---|
| 实用性与创新 25% | 创作、编辑、试玩、交付的完整流程；修改后的证据链校验 | 找真实创作者比较原有工作方式，记录返工原因 |
| 智能体与模型优化 25% | Pi 受限工具、专业 Skills、量化部署、独立检查器与真实修复记录 | 固定陌生题目做 Skills 消融，报告所有失败 |
| 完整性 20% | 前后端、版本、任务记录、取消与重试、独立 HTML | 长时间连续运行与重启恢复测试 |
| 平台适配 15% | ARM64 / GB10 / CUDA 实际运行，本地语言与扩散模型按阶段释放内存 | StepFun 实际调用；如有收益再接入其他 NVIDIA SDK |
| 演示 10% | 可玩的成品、可解释的故障修复、实测镜头 | 两三个精修镜头、稳定的演示节奏 |
| 开发征文 5% | 部署过程、失败样本与选择依据可复查 | 整理为赛事要求的十日开发记录并正式发布 |

这些是取证计划，不是对实际得分或冠军概率的预测。

## 把“稳定、快速、低成本”变成数据

- 稳定：固定工作负载连续运行，记录成功、可重试失败、不可恢复失败；网络故障与模型质量分开统计。不能以两个成功案件推算生产成功率。
- 快速：分别报告首次加载、模型已驻留的生成、排队时间、缓存命中，以及用户拿到可用成品的总时间。播放器切换快来自预生成设计，不能全部归因于 Spark。
- 低成本：按可用产物计算。单件总成本 =（硬件折旧 + 电费 + 存储维护 + 服务费 + 人工返工）÷ 可用产物数；云端对比使用相同质量门槛。已有机器不等于硬件成本为零，日志 API cost=0 也不等于免费。

## 下一轮最值得投入的工作

先找 3–5 位创作者，用未见过的题目制作短案件，固定题目、模型、预算和验收规则，保存完整记录。然后对至少 10 个题目比较有无领域 Skills，检查首次有效提交率、修复成功率、耗时和人工修改量；样本小就如实报告样本数。

影像侧先打磨同一角色的三张参考图与两个短镜头，人工检查脸、服装、背景和连续动作。没有达到要求时，允许导入授权实拍图像或视频素材，不强行把基础模型的质量问题包装成已解决。

当前版本支持导入 PNG/JPEG；导入现成视频、自由问答和配音属于后续功能，演示时不能当作已实现。
