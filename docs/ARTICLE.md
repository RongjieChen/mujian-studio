# 幕间开发记录：让 Agent 交付一部可玩的推理作品

这是一篇待团队发布的开发文章草稿，记录真实开发中遇到的问题。项目阶段跨越多个日期，不伪装成连续十天每天都有成果的日志。实际运行数量、当前版本和新实测以 RELEASE-AUDIT 与 evidence 为准。

## 从交付结果定义任务

我们最先遇到的问题是：一段听起来不错的推理故事，并不自动成为可玩的游戏。物证可能要求先拿到自己，人物的证词可能从未解锁，生成器也可能只解释“已经检查过”，却没有执行检查。

因此幕间把案件写成明确的数据契约：场景、人物、物证、问话、获取条件和结案要求。玩家通过固定动作改变状态，模型不在游玩时临时决定真相。作者仍保留对情节、文字与条件的编辑权。

## Pi 的价值落在工具边界

我们使用 Pi SDK 执行创作流程，并让 Agent 按需读取专业 Skills。模型通过工具提交草稿、查看错误、局部修改、验证和保存。它没有任意 shell 或文件写权限，也无法修改验收器。

后续加固中，我们发现“提交时再检查一次”还不足以证明模型实际执行了要求的工作流，于是记录检查对应的案件哈希。任何新修改都会使这次检查失效，必须重新运行检查才能保存。修复模式还固定了可编辑范围，防止通过删除证据、改写真相或减少结案要求让坏案件看起来通过。

## 能通关和故事合理是两件事

规则检查采用正向证据依赖：获取证据只增加已知信息，条件要求已经持有指定证据。因此可以计算可达信息集合，再用玩家规则重放通关路径。这项检查能找到结构和获取关系的问题，却不能理解全部自然语言。

我们曾刻意在一个案件里加入“完整准确的录像”，证明嫌疑人在作案时段没有离开房间，而作者真相又要求她在同一时段离开。结构检查仍然通过。这个诊断让我们把叙事初审独立出来：模型列出疑点、指向原文字段，程序核对逐字引用。角色说谎可能是剧情，模型需要区分人物陈述与可靠事实，不能将所有不一致机械判为错误。

这项初审只提供作者可核对的线索。我们不会把“模型没发现问题”称为叙事正确性证明，也不会在模型调用失败时返回一个预设高分。

## 单台 Spark 的工程约束

案件模型、SDXL 与 Wan 共享单机统一内存。早期使用 llama.cpp 和 Qwen3-Next 的量化模型完成了生成、编辑与修复；当前版本适配了 vLLM 的本地工具调用与休眠机制。具体配置保留在部署文档与运行记录中。

我们实测过语言模型休眠后再唤醒的过程，并观察到原来超长上下文配置带来过高的整机内存压力。应用实际只使用 32K 上下文，因此缩减服务上下文、并发与批处理预算，并重新验证。这里不能只看 `nvidia-smi` 的单个数字；GB10 上部分显存字段不可用，PyTorch 峰值计数也不等于整机峰值。

视频路径还遇到过缺少 ftfy 依赖、旧版 Diffusers 的 Wan VAE 分块通道问题。解决方式是固定环境、保留失败记录、关闭已验证不兼容的分块路径。我们将加载、生成、缓存和队列时间区分记录，而不把最快的缓存响应当成模型生成速度。

## 对抗测试帮助发现假成功

本轮增加的测试关注错误交付：旧版本恢复能否覆盖新编辑；PNG 文件头后跟垃圾数据是否会被当图片；未知玩家动作是否被误认为结案；模型不调用检查器就提交是否会成功；审阅引用不存在的原文是否会被保存；取消与持久化恰好同时发生时任务状态是否真实。

测试既包含固定规则，也通过模拟 OpenAI 兼容端点驱动真实 Pi 工具循环，还通过 HTTP 启动应用检查请求边界。模拟模型的测试证明工具防线，并不证明真实模型的创作质量；因此真实模型任务、图片视频文件和离线浏览器试玩分别取证。

## 仍然需要真实创作者验证

幕间当前面向短篇推理作品，不是无限世界模拟器。生成画面仍可能有细节问题，人物跨镜头一致性、配音、自由对话和长片制作没有被包装成已完成能力。即使案件可以通关，作者仍要判断动机是否可信、线索是否公平、故事是否值得玩。

下一步最有价值的研究，是让创作者拿自己的故事来修改，比较他们的核对与返工时间，并记录漏检、误报和放弃使用的原因。现有工程结果支持继续试用，不足以宣称已经证明商业价值或普遍节省多少工时。

## 正式档补测

9 月 28 日的正式视频实测输出为 1280×704、121 帧、24 FPS，片长约 5.04 秒，应用作业耗时约 28 分 20 秒，包含模型切换与加载。这让我们明确把产品定位为创作后导出，而非实时生成视频。抽样画面具备渡轮氛围，但没有准确画出信箱与蜡封；关键证据仍由文字和规则表达，避免画面偶然缺失破坏推理。原始 MP4、参数探测和日志随证据保存。
