# DGX Spark 黑客松十日谈：幕间，把一个悬念做成可玩的故事

一个模型可以写出悬疑故事，但作者真正想交付的，是别人能打开、能调查、能走到结局的作品。我们在第三届 NVIDIA DGX Spark 黑客松中制作了「幕间」，尝试把故事创作、游戏规则检查和本地镜头生成放进一个工作台。

本文记录实际开发与测试，不把阶段性工作改写成连续十天都有成果的日记。代码提交主要集中在 9 月 21 日和 9 月 28 日，9 月 29 日再次复核并整理提交材料。界面、示范故事和文章整理均使用了 AI 辅助；真实模型任务、人工修订与失败记录分别保留。

项目代码与部署说明：https://github.com/RongjieChen/mujian-studio

## 先看最后交付了什么

幕间面向短篇悬疑故事作者。创作者输入一个想法，Agent 编排人物、场景、证据与结局；作者在工作台继续修改，检查线索是否可取得，再为场景制作图片或短镜头。最终导出内嵌播放器与素材的 HTML 文件，玩家不需要安装创作环境。

示范作品是《末班渡轮的蓝色信封》：一封寄给对岸旧友的道歉信被调包，玩家在船尾、轮机舱与码头登记间搜集证据，出示物证解锁追问，再指认责任人。当前成品有三个场景、三个人物、六条证据和两种结局。

这份成品经过 AI 初稿、反馈修订和作者终审。版本记录里保留了第四人物残留、时间线矛盾等修订原因；我们没有把它描述成一次生成就能直接发布的作品。

## 第一课：先定义“能完成”

最初的问题不是故事不够长，而是生成结果没有可靠的交付标准。一个看似完整的案件，可能把关键证据锁在它自己后面，也可能让玩家永远拿不到必要证词。

我们先建立案件数据契约：场景、人物、物证、问话、前置证据和结案要求。游玩时由固定规则执行动作，真相在创作阶段确定。条件只要求“已经取得指定证据”，取得证据后不会丢失，因此检查器能够计算可达信息集合，并用与播放器相同的动作规则重放一条结案路径。

这给出了一个范围明确的保证：在该规则与数据下，玩家存在可完成的路径。它不保证唯一解、推理公平或故事有趣。把保证范围说清楚，比展示一个没有依据的“质量分数”更有帮助。

## 第二课：Skills 必须落实到工具边界

幕间使用 Pi SDK 执行创作流程，专业技能包括案件设计、规则审阅、依赖修复、叙事一致性初审与镜头制作。Skills 提供工作方法，真正的约束由工具和程序执行。

Agent 通过受限工具读取案件、提交草稿、局部修改、调用检查器和保存版本。它没有任意 shell 或文件写权限，也不能修改验收器。每次检查绑定当前案件的哈希；改过草稿以后，旧检查就失效，必须重新验证才能保存。

修复任务的权限更窄：只允许调整依赖关系，保护人物、对白、物证文字、真相和结案要求。这避免了“为了通过检查，直接删掉证据或改掉凶手”的假成功。

我们故意把备用电源记录的前置条件设为它自己。真实本地模型修复后，这条证据恢复可达；差异核对确认受保护的故事内容没有被改写。另一次测试把要求越权改写真相的文字放进案件数据，仍用同一套工具边界检验修复结果。对应请求、作业和修复前后数据都保存在仓库 evidence 中。

## 第三课：可通关，不代表没有叙事矛盾

在对抗样例中，我们加入一段“完整且时间准确”的连续录像，称人物在 23:00 至 23:30 一直待在茶室；案件既定真相却写着她在 23:15 出现在走廊。固定规则检查仍然通过，因为获取线索的路径没有断。

为此，我们把叙事初审做成独立的只读流程。模型列出疑点，引用具体原文字段，程序再逐字核对引文。该样例的实际审阅指出录像与真相互斥，并列出需要作者确认的拍摄位置与提供时机问题。审阅工具不能直接修改故事。

这里仍有边界：人物说谎可以是剧情，不能把所有不一致机械判成错误；模型也会漏检和误报。我们没有在调用失败时返回预设高分，也不会把“没发现问题”当作正确性证明。新的生成测试中，前两次尝试未完成有效交付，第三次虽通过结构规则，文字仍有需要作者处理的质量问题，失败记录没有被删去。

## 第四课：单台 DGX Spark，要把内存和时间算清楚

语言模型、SDXL 和 Wan 在同一台 DGX Spark 上工作。媒体任务采用顺序队列，通过语言模型休眠、释放 KV 缓存和结束后唤醒来协调内存。当前语言服务的上下文预算为 32K，同时限制并发与批处理规模；这些是本项目的配置，不代表普适最优参数。

早期使用 llama.cpp 完成文本任务，当前版本适配 vLLM。当前机器既有文本权重目录标称 Qwen3.8-27B-NVFP4，但实际配置架构为 Qwen3_5ForConditionalGeneration，来源尚未独立核实。因此我们披露目录标签与配置，不把现成权重称为自行量化，也不据此宣称用了一个已核实来源的新模型。模型权重不随代码分发。

场景图片使用 SDXL，短镜头使用 Wan 2.2 TI2V 5B，并可用场景图片作为首帧。9 月 28 日正式视频实测得到 1280×704、121 帧、24 FPS、约 5.04 秒的无声片段；应用任务耗时 1699.939 秒，约 28 分 20 秒，包含模型切换与加载，不含排队。

这个结果直接影响产品设计：镜头在创作阶段生成，游玩时读取已经完成的素材。当前产品不依赖实时视频生成。生成画面能传达渡轮氛围，但没有准确复现信箱与蜡封；推理依据由文字证据和程序表达，不把模型画面当成可靠的物证。

素材保存提示输入指纹、种子、模型和耗时。相同输入可以命中缓存，视觉设定改变时提示旧素材过期。我们把缓存响应、媒体生成和完整应用任务耗时分开，避免拿复用文件的速度当作推理速度。

## 第五课：围绕错误交付做测试

最终版本有 35 项自动化测试，Mac 与 Spark 均已通过；9 月 29 日在本地再次复跑，测试与构建通过。覆盖内容包括证据死锁、未知玩家动作、旧版本覆盖、损坏图片、越权修复、未验证就提交、虚构引文、任务取消和中断恢复等。

其中部分测试使用模拟模型端点驱动真实 Pi 工具循环，用来检验工具防线；真实模型能力则另外通过作业日志、修订数据、图片视频和浏览器试玩验证。二者证明的对象不同。

离线导出也单独检查。9 月 28 日保存的浏览器验收记录走完 15 步完整路径，无外部 HTTP 请求和页面错误。9 月 29 日重新在工作台中实际搜证、解锁老陈的追问并完成结案。导出的 HTML 内嵌当前素材与播放器，案件 JSON 则用于继续编辑。

## 现在的不足，以及下一步

幕间已经连接起创作、编辑、检查、素材生成、试玩和导出。配音、自由对话、长片生成及稳定的跨镜头人物一致性，尚不属于完成范围。本轮也没有 StepFun 的真实调用证据，只保留了可配置接入，不能把它列为已经使用的模型。

对这个产品更关键的下一步，是找真实作者和玩家试用：作者究竟减少了多少核对与返工，初审漏掉了什么，玩家是否觉得线索公平、操作清楚、故事值得玩。目前还没有这些用户数据，不能由测试通过推导商业价值。

这次开发最有用的经验，是给生成式 Agent 一个明确的交付对象、有限的工具和可复核的结果。模型负责提出内容，程序守住操作边界，作者保留创作判断。三者接起来，才有机会把一个想法变成别人真正能打开的作品。
